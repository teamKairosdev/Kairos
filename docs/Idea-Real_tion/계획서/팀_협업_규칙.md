## 1. 2인 역할 및 임무 과업 분담

Kairos의 5대 핵심 도메인과 하이브리드 아키텍처(Astro + Nuxt 4 + Tauri + Expo)의 빠른 개발을 위해 역할을 다음과 같이 물리적으로 분담합니다.

```
┌────────────────────────────────────────────────────────┐
│                        팀 HSL (2인)                     │
└───────────┬────────────────────────────────┬───────────┘
            │                                │
            ▼                                ▼
     [ 팀원 A (기획/UX) ]            [ 팀원 B (코어/AI) ]
     - Astro/Nuxt 4 화면 개발       - AI SDK v7 및 모델 라우팅
     - PWA / UXUI 인터랙션 설계     - pgvector / NeonDB 비즈니스 로직
     - PPT 발표 자료 및 문서화      - Redis Cloud 세션 및 가드레일
     - 실전 데모 시연 및 리허설     - Docker 및 Vercel CI/CD 배포
```

### 1.1 상세 분담 영역
*   **팀원 A (Frontend Shell & UX & Presentation)**:
    *   Astro 정적 사이트, SNS 마크다운 피드, 랜딩 페이지 빌드.
    *   Nuxt 4 SPA 모드 UI 구성 (이력서 고도화 스튜디오, 모의면접 UI, ATS 매칭 레이더).
    *   PWA 서비스 워커 및 IndexedDB 로컬 상태 캐싱 UI 적용.
    *   발표 슬라이드 제작 및 라이브 데모 조작 담당.
*   **팀원 B (Backend Core & Database & Infrastructure)**:
    *   Vercel Edge / Nitro 서버리스 API 라우트 및 미들웨어 설계.
    *   Anthropic v7 SDK 연동 및 Evaluator-Optimizer / ReAct 에이전트 루프 구현.
    *   Neon Postgres Drizzle ORM 연동 및 pgvector 코사인 유사도 쿼리 튜닝.
    *   Redis Cloud (Upstash) 시맨틱 캐싱 가속 및 API Rate Limiting 설정.

## 2. Git 브랜치 전략 (Simplified Git-Flow)

대회 마감이 급박하므로 복잡한 Git-Flow 대신 **단순화된 Trunk 기반 개발(Simplified Git-Flow)** 전략을 사용합니다.

```
  main      ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ (Vercel 자동 배포)
                         ▲                             ▲
                         │ (정밀 검증 후 Merge)        │
  dev       ─────────────┴──────────────┬──────────────┴───────────────────── (통합 테스트 브랜치)
                  ▲                     │
                  │ (PR & 리뷰 승인)    │ (Branch 생성)
  feature/  ──────┴─────────────────────▼──────────────────────────────────── (개별 기능 개발 브랜치)
```

1.  **`main` 브랜치 (Production)**:
    *   언제든지 실서버 배포 및 시연이 가능한 **배포 전용 브랜치**.
    *   `main` 브랜치에 직접 커밋하거나 푸시하는 행위는 **절대 금지**합니다.
2.  **`dev` 브랜치 (Integration)**:
    *   팀원 A와 B의 기능 코드가 하나로 모이는 **통합 테스트 브랜치**.
    *   Vercel Staging 환경에 연동되어 실시간 검증을 수행합니다.
3.  **`feature/기능명` 브랜치 (Development)**:
    *   `dev` 브랜치에서 분기하여 개별 티켓이나 기능을 개발하는 브랜치.
    *   예: `feature/resume-parser`, `feature/interview-sse`, `feature/ats-algorithm`.

## 3. PR (Pull Request) 검토 및 머지 규칙

1.  **상호 승인제 (1 Approve Required)**:
    *   `feature/*` 브랜치에서 `dev`로 머지할 때, 또는 `dev`에서 `main`으로 머지할 때 반드시 상대방 팀원의 코드 리뷰 승인(Approve)을 받아야 합니다.
    *   PR 제출 후 슬랙/카카오톡으로 즉시 알림을 주어 4시간 이내에 리뷰를 완료합니다.
2.  **커밋 컨벤션 및 PR 타이틀 명시**:
    *   `feat: [기능]` (새로운 기능 추가)
    *   `fix: [버그]` (버그 및 마이너 오류 수정)
    *   `docs: [문서]` (README.md, 계획서 등 기획 문서 수정)
    *   `refactor: [코드]` (기능 변경 없는 코드 리팩토링)
    *   `test: [테스트]` (단위 테스트 추가)
3.  **PR 단위의 최소화**:
    *   코드 충돌(Conflict)을 방지하기 위해 PR의 수정 라인 크기는 300라인 이하로 유지하는 것을 권장합니다.

## 4. Drizzle 마이그레이션 및 DB 동기화 규칙

두 명의 로컬 데이터베이스 스키마와 Neon Postgres 클라우드 스키마가 어긋나는 현상을 완벽히 통제해야 합니다.

1.  **스키마 수정 절차**:
    *   `db/schema.ts` 수정 시 반드시 로컬에서 마이그레이션 생성 명령 실행:
        ```bash
        pnpm drizzle-kit generate
        ```
    *   생성된 `drizzle/` 폴더 내부의 SQL 파일들을 스키마 코드와 함께 동일한 Git PR에 묶어 전송합니다.
2.  **스키마 변경사항 수신 시**:
    *   상대방의 스키마 변경 PR을 풀(Pull)한 후, 본인의 로컬 개발 컨테이너 또는 Neon DB에 즉시 마이그레이션을 푸시 적용합니다:
        ```bash
        pnpm drizzle-kit push
        ```

## 5. 데이터 백업 및 비상 장애 대응 가이드 (Rollback)

1.  **배포 실패 및 장애 시**:
    *   `main` 브랜치 배포 후 예기치 못한 에러 발생 시, 롤백을 신속히 수행하기 위해 최신 정상 빌드 커밋 해시로 즉시 리버트(Revert)합니다:
        ```bash
        git revert <commit-hash>
        git push origin main
        ```
2.  **로컬 데이터 유실 방지**:
    *   데이터베이스 마이그레이션 작업 전에는 반드시 Neon 대시보드에서 **DB 브랜치 백업(Branching)** 기능을 사용해 현재의 데이터를 스냅샷으로 보관합니다.
